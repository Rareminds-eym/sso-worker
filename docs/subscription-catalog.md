## Implemented contract

- `createPlanIdentity(productId)` creates an independent UUID and opaque `pln_` code from server cryptographic randomness. Persistence must enforce uniqueness; generation alone is not a database uniqueness guarantee.
- `validatePlanIdentity(value)` accepts the new identity contract. It is deliberately not applied to legacy rows, including Hybrid, until their explicit consumer migration is ready.
- `validatePlanRevision(value, registry)` validates explicit schema versions 1 and 2 against trusted product, audience, currency-precision and feature-type registries. It rejects unknown fields, ambiguous prices, duplicate features, unresolved self-service terms and implicit limits. It returns detached deeply frozen values. Schema 2 metered grants require `limit: { kind: 'allocation_policy' }`; numeric metered values are rejected.
- `selectEntryPlan(productId, audience, bindings, candidates)` resolves exactly one configured eligible reference and requires an explicit published-revision identity. Its candidates must come from the trusted publication owner; it does not prove publication or authorize access itself.
- `stagePlanRevision(client, value, registry, actorId)` validates authoring data, calls the service-only staging RPC through the existing `DbClient`, and checks the returned snapshot and actor against the request. A staging receipt contains only the immutable draft, staging actor and database timestamp. It confers no purchase/access/publication permission.
- `readPlanRevision(client, revisionId, registry)` queries a bounded exact UUID reference and validates the stored snapshot. Missing, ambiguous, malformed or mismatched records are errors. This is a current authoring reader: if a trusted registry no longer recognizes historical configuration, it rejects it; archival evidence reads will need a separate explicit contract.
- `validateCreditAllocationPolicy(value, revision, registry)` validates an explicitly revision-bound candidate policy for included or purchased credits. See the credit contract below; it does not allocate, persist or publish credits.
- `validatePlanRevisionBundle(value, registry)` binds a schema-2 draft and exactly one included-credit policy into a detached immutable envelope. The envelope has `schemaVersion: 1`, `draft` and `includedCredits`. Its schema version is independent of the nested draft/policy versions. Enabled metered features and every eligible audience must have explicit included terms. Zero included units remain explicit. Purchased top-ups are separate offers and cannot occupy this position.
- `stagePlanRevisionBundle(client, value, registry, actorId)` stages both terms through one existing-client RPC and verifies the entire returned content and actor. `readPlanRevisionBundle` reads both snapshots from one bounded exact revision record. The old unbundled staging/read adapter rejects schema 2, preventing loss of credit terms. No automatic schema conversion is attempted.
- `readCanonicalPlanInventory(client)` reads only canonical plan identity/display/product/availability/audience fields through the existing database client. It includes legacy codes, null product references and inactive rows for administration; it never interprets them as purchasable offers. `SsoWorker.getSubscriptionCatalogInventory()` exposes this read through the existing private binding.

## Draft schema scope

The draft carries a revision UUID/number, plan identity, display name, audience keys, purchase mode, price options and typed feature grants. Prices use integer minor units with registered currency precision, explicit billing intervals, quantity basis and eligible audiences. Numeric limits distinguish finite, unlimited and contract-required values. Schema 1 metered grants have finite or negotiated terms; schema 2 instead delegates all metered quantities to the bound allocation policy. Neither implies unlimited credits.

These schemas are authoring foundations, not a complete BRD publication format. The bundle now joins included-credit terms to a draft for immutable staging. Lifecycle policy references, revision approval/effective-time metadata, add-on relationships and coordinated application-rule publication remain unfinished. Do not use a draft or bundle as permission to purchase, allocate credits or grant access. A contact-sales proposal with unresolved terms is not an activatable contract.

## Candidate credit-allocation contract

[The credit-policy validator](../src/lib/subscriptions/credit-policy.ts) separates commercial allocation terms from an aggregate numeric feature limit. The existing application allocator reads a single numeric amount per metered feature; it cannot by itself represent institutional admin credits plus credits for each managed learner on a different cadence. This worker contract prepares the commercial terms; application ledger ownership stays with SkillPassport and no private cross-runtime import is introduced.

Every candidate has its own UUID, the exact draft revision UUID, explicit `included` or `top_up` funding and rule UUIDs. Each rule names an enabled registered metered feature, a registered pool, a recipient kind (`subscriber`, `organization`, `managed_learner`) and eligible audiences. Pool keys are semantic registry keys, like feature keys; plan codes remain opaque. Quantities are units per recipient per occurrence and must fit the existing ledger's PostgreSQL integer amount (maximum 2,147,483,647 per rule occurrence). Aggregate calculations still need checked arithmetic in the future allocator; no implicit splitting is performed. Zero included quantity is an explicit absence of included units, not an implied allocation; purchased finite quantities must be positive. Negotiated quantity is permitted only for contact-sales authoring and cannot activate a contract.

Cadence is explicitly activation, subscription period, monthly or purchase. Monthly rules require an applicable registered time-policy reference. Expiry is explicitly subscription end, allocation-period end or a number of months with a registered time-policy reference. Period-end expiry requires a recurring cadence. Time policies must eventually resolve anchoring, timezone and calendar-boundary behavior; this validator only checks references and does not calculate dates or select a default. Billing cadence does not silently determine credit cadence.

Purchased credits require purchase cadence and explicit six-month expiry, matching BRD section 13, or an applicable registered commercial expiry approval. Included rules cannot use purchase cadence. Rollover is explicitly absent or backed by a registered approval. Registries must be assembled by the trusted owner and filtered for the specific revision, commercial scope, validity and authorization; arbitrary existing IDs or client-supplied sets do not establish applicable approval. This layer does not approve finance/legal policy.

Duplicate rule UUIDs and overlapping feature/pool/audience scopes are rejected even when cadence differs. Separate admin and learner pools can legitimately target the same metered feature. Every enabled metered feature and revision audience requires explicit included terms; a top-up candidate can cover a subset but cannot be empty. Returned values are detached and deeply frozen, and missing/sparse elements are rejected through the same internal validation boundary as catalog drafts.

The old `stagePlanRevision` remains schema-1-only. Do not append credit fields to draft JSON: unknown fields remain errors. Use the explicit bundle to stage schema-2 catalog terms and included-credit policy together; its metered marker removes a competing catalog allocation amount. The prepared migration stores both snapshots in one immutable row and checks both on exact replay. Standalone/top-up candidates are not persisted by this adapter. Approval loading, credit tariffs, population snapshots, scheduling, idempotent allocation, consumption order, expiry ledger entries, refund/settlement and activation wiring remain unfinished. No credit balance or ledger entry is created by validation or staging.

# Publication completeness preparation

Unrelated configuration sections are preserved. Version selection is explicit configuration, with no retry or alternate version on failure. No current owner configuration was upgraded or seeded by this source extension.

This proves completeness against configured coverage only. It does not prove that administrators configured the complete BRD profile, qualitative value semantics, approval, application-rule readiness, authorization or publication eligibility. No published revision pointer or activation operation is introduced.
